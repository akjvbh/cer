# 开发流程

## 每次动手前

1. **先读再改**：改任何文件前先读它，至少读要动的函数所在区间。不要凭记忆假设代码长什么样。
2. **先说计划再改**：一次涉及 3 个以上文件，先用 4 到 6 条要点说明「改哪个文件、为什么、怎么验」，等我确认或你写完这一步再继续。
3. **一次只做一件事**：不要在一个回复里同时加新功能、重构旧代码、改样式。

## 执行中

4. **小步验证**：每完成一个能独立运行的单元就实际跑一次。禁止写完 5 个模块再「应该能跑」。
5. **不伪造**：不要声称运行过没运行过的命令，不要粘贴你没看到的输出，不要编造测试结果。命令失败就把真实报错原样贴出来。
6. **报错处理顺序**：读完整 traceback → 定位第一处自己写的代码 → 只改这一处 → 再跑一遍。禁止一次改五处「试试看」。
7. **不要大面积重写能工作的模块**。要重写先说明理由和影响范围，等我点头。
8. **不确定就问**：页码语义、格式映射、第三方库实际能力这类「猜错会静默出错」的地方，先列选项让我确认，不要自己拍板。

## 每次收尾

9. 跑 `python tests/smoke.py`，贴真实输出。
10. 说明：改了哪些文件、各干什么、哪些是降级实现、还有什么没做。
11. 提交：`git add -A && git commit -m "stage N: <一句话>"`。每个阶段一个提交，便于回滚，也是比赛要展示的过程证据。
12. 依赖只装 `requirements.txt` 里有的或本阶段明确需要的，装之前说明用途；不要顺手升级已装的包。

## 输出风格

- 中文，结论先行，先给结果再给解释
- 不写「我建议」「可以尝试」这种模棱两可的话；要么做了并给出验证，要么说明为什么没做
- 贴代码时只贴改动的函数，不要整文件重贴
- 不确定的地方明确标注「假设：」「风险：」「待确认：」
