# 纠偏提示词

出问题的时候不要顺着它继续聊，直接换一条新的消息，用下面场景对应的提示词。每个场景的用法写在标题下面。

---

## 场景 A：启动就报错、页面打不开

**什么时候用**：`python main.py` 一跑就 traceback，或者浏览器 404 / 一直转圈。

```
启动失败了。先不要改代码，按这个顺序做：

1. 把你实际执行的命令和完整的报错原文贴出来（不要概括、不要省略 traceback 中间行）。
2. 判断错误属于哪一层：解释器/虚拟环境、import 依赖缺失、路由注册、端口占用、还是业务代码。给出判断依据。
3. 只修最根本的那一处，改完立刻重新执行同一条命令验证。
4. 如果第一次修改后仍然失败，不要连续试错，先把「我观察到的事实」列出来（什么命令、什么退出码、日志哪一行），再提出最多 2 个假设，让我选。

不要在我看不到结果的情况下声称「已经修复」。
```

## 场景 B：转换结果不对（文件坏了、页数错了、内容空）

**什么时候用**：能下载到文件，但打开是空的、页数不对、乱码、中文变方框。

```
转换结果不正确：<描述现象，例如“删第 2 页后页数没变”>。

请这样做：
1. 写一个最小复现脚本 `tests/_repro.py`，只依赖 sample 文件，直接调用对应的转换函数（不走 HTTP），打印输入页数、输出页数、首页旋转、输出文件大小。
2. 把脚本的真实输出贴出来，让我确认复现了。
3. 定位到具体是哪一行逻辑导致，说明「期望值 vs 实际值」。
4. 只改这一处，再跑一次脚本，对比修改前后的数字。
5. 脚本保留在 tests/ 下并命名清楚，作为回归用例。

不要顺手"优化"其它 handler。
```

---

## 场景 C：它改坏了，要回滚

**什么时候用**：改之前能用，改完一堆功能坏了，或者它开始大范围重写。

```
停。当前这一轮改动让原本能用的功能出现了回归，现在不要继续改代码。

请做三件事：
1. `git status --short` 和 `git diff --stat`，告诉我这轮改了哪些文件、多少行。
2. 把这轮改动区分为「必要的」「顺手改的」「破坏性的」三类，逐条列出。
3. 建议回滚方案：是 `git checkout -- <文件>` 局部回滚，还是 `git stash` 整轮收起。给出具体命令，但**先不要执行**，等我确认。

回滚之后，重新用一句话说明你原本想解决的问题，我们换一个更小的改法。
```

## 场景 D：太慢、内存爆、卡住

**什么时候用**：转换一个 2MB 文件要几分钟；或者风扇狂转、内存涨到几个 G。

```
性能有问题：<描述，例如“一个 100 页 PDF 转 JPG 用了 3 分钟”>。

先测量，再优化：
1. 在关键步骤加计时日志（`time.perf_counter()`），打印：打开文件、逐页渲染、写文件、压缩各自的耗时和峰值内存。
2. 贴出测量结果，指出瓶颈在哪一步。
3. 给出最多 2 个优化方案，说明各自的代价（内存换速度 / 质量换速度）。
4. 先实施方案 1，改完用同一份文件再测一次，给出前后对比数字。

不要在没有测量数据的情况下改算法。
```

## 场景 E：Office 卡死、WINWORD 残留

**什么时候用**：docx→pdf 一直不动；任务管理器里有一堆 WINWORD.EXE。

```
Office 自动化卡住了。按这个顺序处理：

1. 检查代码里是否满足：每个 COM 线程都调了 CoInitialize、转换有超时、超时后执行了 taskkill、全局有串行锁。逐项告诉我现状（贴代码行号）。
2. 缺哪项补哪项，补完在超时分支里加日志「Office 超时，已结束进程」。
3. 加一个 `OFFICE_ENABLED` 环境变量开关，设为 0 时所有 Office 转换直接走兜底，便于我在演示机上绕开这个问题。
4. 验证：故意把超时设成 1 秒跑一次 docx→pdf，确认服务在 2 秒内返回错误、任务管理器里没有残留 WINWORD。

演示时如果本机 Office 不稳定，我要能一键切到兜底模式。
```

## 场景 F：它在编造（说测试过了其实没过）

**什么时候用**：回复里出现「已通过测试」「功能正常」但没有真实输出。

```
不要给结论，只给证据。

从现在开始，每次声称"完成/通过/修复"时必须同时给出：
1. 实际执行的完整命令
2. 命令的原始输出（至少 5 行，包含退出码）
3. 如果结果是文件，给出文件路径和大小（`ls -l` 或 `Get-Item` 的输出）

没有这三样的内容，视为未完成。现在请把你上一条回复里提出的结论逐条对照这三条要求，说明哪些有证据、哪些没有。
```

## 场景 G：界面乱了 / 样式不对

**什么时候用**：布局错位、深色主题下字看不见、按钮点不到。

```
界面有问题：<截图或描述>。

1. 先定位是结构问题（HTML 层级）还是样式问题（CSS 优先级/变量），说明判断依据。
2. 如果是主题相关，检查 `data-theme` 作用域和 CSS 变量的覆盖顺序，把相关规则贴出来。
3. 只改一处，然后告诉我用浏览器怎么验证（哪一步、看什么现象）。
4. 不要为了对齐引入 flex/grid 之外的 hack，也不要新增内联样式。

我需要它在 1280px 和 600px 两种宽度下都正常。
```

---

## 场景 H：需求变更，要加功能

**什么时候用**：比赛前想加一个亮点功能。

```
我想加一个功能：<描述>。

先不要写代码，回答四个问题：
1. 这个功能需要动哪些现有文件？会不会破坏现有接口？
2. 最小可用版本是什么（能演示就行），可以砍掉什么？
3. 需要新增依赖吗？在没网的演示机上能跑吗？
4. 需要多久？如果超过 1 小时，给出更小的替代方案。

我确认方案后你再动手，一次只做这一个功能。
```

## 场景 I：代码越写越乱，要收口

**什么时候用**：单个文件超过 1000 行，或者你发现自己看不懂它刚写的代码。

```
现在做一次收口，不要加新功能：

1. 列出当前每个文件的职责和行数，指出哪些函数超过 80 行、哪些文件超过 600 行。
2. 给出拆分方案（只拆文件、不改变行为），说明拆完每个新文件的职责。
3. 拆分前后各跑一次 `tests/smoke.py`，贴出两次输出证明行为一致。
4. 拆分单独一个 commit，不要和功能改动混在一起。

超过 600 行的文件优先拆，但一次只拆一个。
```
