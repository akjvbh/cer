# 演示与提交

功能做完不代表能拿分。这个文件里的提示词用来把「能跑的东西」变成「能讲的成果」。

---

## 1. 生成演示脚本

**用法**：功能全部跑通后，贴给它，让它按你的真实功能排一场 5 分钟的演示。

```
现在不要改任何代码。基于当前项目已经实现的功能，写一份 5 分钟现场演示脚本。

要求：
1. 时间轴精确到 30 秒，例如「0:00-0:30 开场，说明解决什么问题」。
2. 每一步写清楚：点哪个标签、拖入哪个文件、预期屏幕上出现什么、我该说哪句话。
3. 演示顺序按「观众最容易看懂」排，不要按开发顺序排。开场不要讲技术栈。
4. 必须包含一个"翻车也不怕"的环节：提前准备好降级路径（例如 Office 不可用时切兜底、翻译未配置时的提示），并写明如果现场出问题我该说什么。
5. 结尾留 40 秒讲技术亮点：本机处理不上传、Office 不可用自动降级、页码语义的坑、AI 翻译保留版式。
6. 演示前 10 分钟的准备清单：要关闭的窗口、要准备好的文件、要提前跑一遍的命令。
```

## 2. 准备答辩问答

**用法**：让它在提问前先把可能的追问列出来，并给出基于真实代码的回答。

```
假设评委只给我 3 分钟提问，请列出最可能被问到的 10 个问题，并按难度排序。

要求：
1. 每个问题给出一句话回答（30 秒内能说完），再用一句话点出证据在哪个文件/哪一行。
2. 至少覆盖：为什么不用云端转换、Office 依赖怎么解决、PDF 页码和坐标怎么保证不出错、翻译的版式怎么保留、并发和超时怎么处理、安全上做了什么、如果要做成 SaaS 需要改什么。
3. 对于「你们这个和 WPS/在线转换有什么不同」这类问题，回答要具体到能力和数据流向，不要空谈。
4. 标出哪两个问题我可能答不好，并给出补强的办法（补代码注释、补 README 段落、准备一段 20 秒的代码走读）。
```

## 3. 最终提交前核查

**用法**：交付前一晚跑一遍，让它逐项给证据。

```
现在做提交前核查，不要改代码，只输出核查结果表。

逐项检查并给出证据（命令 + 输出摘要）：
1. 干净环境能起来：删掉 .venv 后重新 `python -m venv .venv && pip install -r requirements.txt`，再启动一次。失败就说失败。
2. README 里的每条命令都能照抄执行，把不能执行的列出来。
3. 关掉 Office 的场景：设置 OFFICE_ENABLED=0 启动，确认转换主链路仍可用，界面对降级有说明。
4. 没有 .env 时启动，翻译区域显示「未配置」而不是报错。
5. 三个测试脚本全绿，贴输出。
6. git 历史：每个阶段一个 commit，贴 `git log --oneline`。
7. 仓库里没有大文件、没有 uploads/outputs/.env，贴 `git ls-files | Select-String -Pattern "uploads|outputs|\.env"`。
8. 已知限制是否都写进 README。
9. 演示要用的样例文件是否都在 samples/ 下，且都能跑通。

最后给出「可以提交 / 不能提交 + 阻塞项」的结论。
```

## 4. 处理"必须用 Qoder"这条规则

比赛如果要求证明是用 Qoder 做的，建议保留这几样，评审核查时很有说服力：

- `.qoder/rules/` 里的规则文件（说明你给 AI 定了什么边界）
- 每个阶段的规划输出（`/plan` 或 Spec 模式生成的计划）截图或导出的 Markdown
- `git log`：每阶段一个提交，提交信息写清阶段
- 一份 `docs/AI-USAGE.md`，用下面这段提示词生成

```
写一份 docs/AI-USAGE.md，说明我是怎么用 Qoder 完成这个项目的。

内容包括：
1. 工作方式：先规则约束、再规划、再分阶段实现、每阶段验证并提交。
2. 规则文件清单，以及每个规则解决什么问题。
3. 五个阶段各自的目标、产出的文件、验证方式。
4. 三个「AI 想偷懒/跑偏，我是怎么纠正的」真实案例，写清楚当时的提示词和结果。
5. 哪些部分是我自己写的（例如需求、验收标准、演示脚本），哪些是 AI 生成的。

只写真实发生过的事，不要编造案例。
```
